# Jellyfin 新增连接的凭证校验

## 复现证据

用户反馈网页可以登录，但 Glide 新增 Jellyfin 来源时显示“服务器未返回有效的登录凭据”。目标公共接口返回 HTTP 200 和 Jellyfin 12.2.0。

使用独立 QA 包收集一次真实登录的字段特征。账号密码由用户在手机中输入，未导出请求体、用户名、密码、令牌、用户标识或完整响应。

优化编译的 `2.0.1 (6)` 复现了同一问题：

- 服务器返回 JSON，含非空的 32 字符 AccessToken，未检测到令牌控制字符。
- User.Id 存在且长度为 32，无空白、路径分隔符、大括号、等号或句点。
- 本地 `CharacterSet.alphanumerics.union(...)` 的成员检查返回 false，因此被 `validateSession` 拦截。

修复包的后续真机报告进一步确认：同一服务器返回的 User.Id 是合法的 32 字符十六进制标识，旧 `CharacterSet` 检查仍为 false，逐字节 ASCII 检查为 true；该登录凭证可成功通过 `/Users/Me` 认证。因此这是合法标识被客户端本地校验误拒绝，并非服务器未返回凭证。

脱敏字段报告见 `Testing/Jellyfin-Login-2026-11-18/before-fix.json`。

## 修改

对用于请求路径的用户标识改为显式逐字节检查，允许 ASCII 字母、数字、连字符和下划线。保留非空令牌、令牌控制字符和用户标识路径边界检查。

新增标准 Jellyfin/Emby 标识、UUID、令牌样例及非法路径标识回归。完整核心测试通过：11 项 XCTest + 297 项 Swift Testing，共 308 项。

QA 登录页额外检查 `/Users/Me` 是否对应此次认证用户，并读取 `UserViews` 验证媒体库接口可用。旧保存会话也可用于对照服务器实际返回的标识格式；所有导出字段均为格式特征或计数。

## 验收状态

修复后的优化 QA 包及主应用 Release 包 `2.0.1 (7)` 均已构建成功，深层签名检查通过。

用户重新连接并解锁后，已完成以下验收：

- 用户在手机内再次输入账号密码，登录验证通过。
- `/Users/Me` 返回的用户与本次认证用户一致，`sessionAuthenticated=true`。
- `UserViews` 成功读取 9 个媒体库。
- 保留了原始用户标识，没有修改服务器账号或配置。
- 已覆盖安装主应用 `com.songpeng.glide` 的 `2.0.1 (7)`，并成功启动；既有应用数据保留。

修复后脱敏报告见 `Testing/Jellyfin-Login-2026-11-18/after-fix.json`。QA 页中的诊断登录没有新增到主应用来源列表；用户可直接在主应用中重新添加此服务器或重新登录现有来源。
