# 1.3.0（6）Jellyfin 开播前选择原画传输

日期：2026-10-16。开发验证版，未发布。

## 原片反馈

用户确认：同一文件离线播放流畅；Jellyfin 在线直放打开约 5–6 秒仍有停顿，手动选择“尝试原画兼容”后不卡顿。这个人工对照支持优先使用已奏效的原画传输方式，未附新诊断，不能据此定位具体网络设备、NAS 读取或 HTTP 范围读取的根因。[构建（5）记录](Glide-1.3.0-Original-Transport-2026-10-16.md)。

## 本次行为

- Jellyfin 自动播放解析到原画直放时，如果视频长边至少 3840 像素，或声明码率至少 20 Mbps，且服务器未明确拒绝 Direct Stream，先协商原画分段，成功后才安装播放器媒体项。无需先播放几秒、卡顿、蓄缓存，再手动切换。
- 初次能力字段缺失时也可进行能力协商；兼容响应必须明确支持 Direct Stream，且 URL 经现有校验确认 `VideoCodec=copy`。请求关闭视频编码，允许原视频／音频复制；需要时允许仅转换音频，不主动降低分辨率或视频码率。
- 协商拒绝／失败时复用已解析的直放资源；兼容流加载失败或未出首帧时，保留同一媒体版本、位置、倍速和播放／暂停意图，返回直放一次。后续恢复不能绕过同次会话的一次试用预算；此次回退本身不请求 1080p／720p 视频编码。
- 普通低码率直放、已为 HLS 的资源、服务器明确拒绝 Direct Stream 的资源不触发这次预先协商。缺少负载元数据时沿用原先路径及手动试用入口。
- 离线副本仍优先本地播放；用户点“在线播放”后，服务器资源同样采用上述选择，已下载文件保留。
- 下一集预热识别到这类候选资源后，不读取原文件媒体数据，也不提前启动分段任务，避免为尚未播放的视频占用供流。
- 未增加网络 VLC、WebDAV 能力或持久化服务器偏好。诊断 schema 保持 8，新增 `transport_preferred_original`，记录实际最终路径。

## 验证记录

原创样例沿用 2160×3840、H.264 Main／5.2、SDR、50 fps、约 29.7 Mbps、60 秒 MP4。直放存在人为供流间隔；替代 HLS 通过 `ffmpeg -c copy` 从同一素材生成。[既有码流一致性证据](Glide-1.3.0-transport-video-hash.json)。服务器仅绑定 127.0.0.1，不访问用户媒体或凭据。

Core 回归通过 97 项（93 项 Swift Testing、4 项 XCTest），日志 `/tmp/Glide4K/core-build6-r2.log`。新增策略边界覆盖横／竖 4K、20 Mbps 门槛、能力缺失／拒绝、低码率、未知负载、本地副本和已分段／视频编码资源。

首轮 `/tmp/Glide4K/Transport-Build6-R1.xcresult` 在位置断言失败：测试使用 `recordsProgress: false`，该模式按产品既有规则忽略新开播的历史定位参数，实际从头播放；不是传输切换丢失位置。该轮已确认原生 4K 首帧直接来自原画重封装。随后改用有历史的播放模式验证明确初始定位，并增加首次能力字段缺失、分段 URL 加载失败、离线定位 12 秒后转在线的场景。

最终 `/tmp/Glide4K/Transport-Build6-R2.xcresult` 通过（测试本身 123.978 秒），生产控制器 20 项检查通过：

- 第一次打开从第 3 秒续播，首帧即为原生 2160×3840 的原画重封装；继续推进到第 15 秒，诊断报告原生停顿 0、缓冲次数 0、恢复次数 0。首帧前后没有安装直放媒体项，服务端也没有收到直放视频数据请求。
- 再次打开，初始能力字段缺失时经额外协商确认视频复制；第 20 秒暂停起播保持位置，之后可继续播放。
- 缺少负载元数据时保留直放和手动入口；下载在播放期间完成后，手动原画传输仍请求网络并保持暂停及位置。
- 真正下载该原创 MP4 后，默认从本地打开；定位到约 12.021 秒再切“在线播放”，自动使用原画分段，离线副本、暂停和进度均保留。
- 兼容协商被拒绝时复用直放资源，保留媒体版本、初始定位和暂停；兼容 URL 返回不存在错误时，返回同一媒体版本的直放一次，未重复兼容协商，也未请求 1080p／720p 编码。
- 服务器明确不支持分段时，原生第二次停顿没有重复主动蓄缓存。全流程共 6 次复制协商，测试服务逐次断言禁止视频编码。
