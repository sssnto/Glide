# Glide 1.1.0（4）缓冲恢复修订

日期：2026-10-10。构建 3 已提交 GitHub；本轮针对「首帧已出现，加载中切到转码」进行独立修订，不能沿用之前的实机确认作为本次验收。

## 代码中的触发原因

原缓冲结束回调在正常播放恢复时检查历史卡顿：一次等待超过 8 秒，或两次累计至少 5 秒，就立即关闭已恢复的流并开启视频转码。25 秒通用看门狗也仅观察时间停滞，没有考虑缓存是否仍在增长。这些分支可以让原本能正常解码的大码率视频在网络暂时波动后误降级；尚未取得用户此次诊断，不能据此断定其样本只经过这个分支。

## 新行为

- 已恢复的缓冲不触发转码，也不累计为下一次降级依据。缓冲时长与次数仍记入诊断，明显等待恢复后仍提高预取目标。
- 首帧后的看门狗使用 AVPlayer 实际播放时间与当前位置的连续可用缓存。持续停滞至少 45 秒，且连续可用缓存至少 20 秒没有增长，才触发自动恢复；缓存仍增长时允许更多时间，连续停滞最多等待 90 秒。
- 进入 `.playing`、播放时间继续推进、主动暂停、正在定位时清除卡顿观察，避免恢复瞬间及用户操作被算作失败。正常倍速调整不改变当前播放路线。
- 无首帧的起播超时、实际图层无画面、item 失败、HDR 输出不兼容保留原有恢复路径；不把「曾出过一帧」视为永久兼容。
- 诊断继续使用 schema 5，新增事件 `buffering_recovered`（已恢复的明显缓冲）、`buffer_wait_timeout`（当前持续停滞超时）；不加入文件路径或认证信息。首帧后的网络等待不写入需要视频转码的学习记录。

## 验证

- 核心测试：80 项通过，覆盖恢复后保留流、短等待不累积、连续等待与无缓存进展的双条件、有缓存进展的等待上限、主动操作与倒退时间重置；现有质量、字幕、HDR、目录、离线等核心回归通过。
- iOS arm64 Release 未签名编译通过，产物版本为 `1.1.0 (4)`，不等同于实机启动或上传。
- 本地 AVPlayer 缓冲集成回归 `testRecoveredBufferingRetainsTheWorkingVideoStream` 通过（151.735 秒）。使用演示原码流生成 90 秒 HLS，第四分段延迟 24 秒；已确认首帧出现、实际缓冲 22.882 秒、恢复播放越过 30 秒进度后仍为原画重封装，仅一次 PlaybackInfo，`recoveryCount = 0`、`requestedQuality = automatic`，预取目标提高为 45 秒，包含 `buffering_recovered`。初次测试的焦点、版本标识与延迟位置／观测进度前提已修正后才计为通过。
- 既有兼容播放用例 `testAutomaticPlaybackRecovery` 通过（110.939 秒），确认兼容 HLS 出画面、缓存范围与控制操作。本次模拟器已有该测试影片的转码学习记录，实际仅一次 PlaybackInfo，不能算作首次黑屏识别回归；首次黑屏恢复分支未修改，相关核心策略测试通过，真实故障样本仍列入下方实机复测。首次运行因切换本地 fixture 后目录缓存仍含旧条目而未进入播放，补充下拉刷新测试前提后重跑通过。
- 发布预检、fixture Python 语法检查与 `git diff --check` 通过。本轮未归档上传，也未提交 GitHub。

## 实机复测

1. 用此前误切转码的视频，从头播放 1× 至少 3 分钟。出现画面后经历缓冲，网络恢复后应保持原画／原画重封装，继续当前位置；导出诊断检查 `buffering_recovered`、缓冲秒数与恢复次数。
2. 同一视频在 2× 播放，暂停、继续、缓存内外拖动，切换到下一段再返回。短暂等待不应触发转码；普通控制与定位仍有效。
3. 在可恢复的短暂弱网中，验证原画恢复。持续断网或长期供给不足时仍允许自动恢复；检查 `buffer_wait_timeout`，不要把无期限等待作为保留原画的方式。
4. 对之前有声音无画面、HDR 偏绿、原生不支持的样本复测，确认真实兼容故障仍能进入恢复。服务端主动转码与客户端首帧后降级要按诊断事件区分。

真实 NAS 网络波动、码率及服务器转码性能仍需用户实机验证，本轮不声称已测量改善所有媒体的卡顿率。
