# 1.3.0（4）4K／50 帧缓冲复核

日期：2026-10-16。开发验证版，未发布。

**后续用户原片复测未通过。** 构建（4）仍有频繁缓冲，主动等待两次均到达时限，未达到缓存目标。详见 [用户复测分析](Glide-1.3.0-4K-build4-user-followup-2026-10-16.md)；下述模拟器通过记录不能视为此问题已解决。

用户在构建（3）复测后反馈：等待后可以继续，但很快再次停顿。新诊断为原画直放，2160×3840 H.264 Main／5.2、50 fps、8-bit SDR，来源声明总码率 28.657 Mbps。导出时主动蓄缓存已触发，前方可用缓存仅 0.100 秒，尚无续播完成事件。观测传输速率 50.277 Mbps 和零上报丢帧，不能证明整个会话持续带宽充足，也不能据此排除解码或系统资源限制。

已移除会话 ID 的 [构建（3）用户诊断](Glide-1.3.0-4K-build3-user-diagnostic.json)。其中 `bufferingSeconds` 只累计已结束的缓冲，不能用来计算正在进行的主动等待时长。

## 本轮改动

- 缓存主动等待时，除暂停之外，在 AVPlayer 已就绪且速率为零时调用 `preroll(atRate:)`，明确请求准备媒体管线。预装载完成不等同于已获得目标缓存，续播仍检查连续可用媒体范围和平台容量，并保留原来的最长 15 秒主动等待。
- 暂停、定位、停止、切换文件和等待结束均取消预装载。回调校验加载代次及预装载请求 ID，不能替用户自动恢复旧播放。倍速变化时重建预装载请求。
- 诊断 schema 8 增加当前／上次主动等待时长、进行中缓冲时长、原生播放状态、缓存满与可持续播放预测，以及最新 access-log 事件的传输字节／传输耗时。传输统计对应最新事件，事件更新时可以重置，不能当作全会话累计值或瞬时带宽。
- 等待期间按墙钟刷新诊断，不依赖已暂停的媒体时钟；原画路由、缓存目标与清晰度不因本轮调整而改变。

Apple 对 `preroll` 的定义是准备播放管线，要求播放器就绪且速率为零；没有承诺必定填满指定时长：[官方 API](https://developer.apple.com/documentation/avfoundation/avplayer/preroll(atrate:completionhandler:))。`preferredForwardBufferDuration` 仍是偏好，系统可因资源消耗而少缓存：[官方说明](https://developer.apple.com/documentation/avfoundation/avplayeritem/preferredforwardbufferduration)。因此，本轮是针对暂停等待链路的补强，尚未确定用户原片频繁停顿的唯一根因。

## 验证

原创素材改为 2160×3840、50 fps、H.264 Main／5.2、8-bit SDR、约 29.665 Mbps、60 秒。参数和 SHA-256 见 [ffprobe 记录](Glide-1.3.0-4K50-fixture.json)。脚本保留上一轮 24 fps 默认值，新参数为 `--fps 50 --bitrate 28`。

HTTP Range 服务继续注入 3 秒、8 秒间歇，其他 2 MiB 数据块的间隔设为 0.4 秒。只有原创样例、固定 loopback 服务；没有用户服务器或凭据参与。

Release 未签名归档 `/tmp/Glide4K/Glide-1.3.0-4.xcarchive` 已通过；确认调试网络入口未进入可执行文件，中文后备字体仍在包内且 SHA-256 与源码一致。独立「Glide 兼容验证」1.3.0（4）已签名构建并成功安装到连接的 iPhone 13 Pro Max；设备锁定导致自动启动被 iOS 拒绝，本轮没有声称真机原片流畅性已通过。
