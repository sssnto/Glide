# 1.3.0（5）Jellyfin 原画传输恢复

日期：2026-10-16。开发验证版，未发布。

## 问题与证据

用户在构建（4）的同一局域网 4K／50 帧原画直放仍反复停顿，主动预装载两次到达 15 秒时限，最近一次只有约 1.215 秒有效缓存。随后按“下载原文件、系统播放”的对照步骤反馈“离线播放不卡顿”；没有附带离线诊断。该反馈支持优先处理远程供流与读取路径，不能将原因进一步确定为某段 Wi-Fi、NAS 读取、Jellyfin HTTP 响应或 AVPlayer 范围读取行为。[构建（4）原片复核](Glide-1.3.0-4K-build4-user-followup-2026-10-16.md)。

## 最终行为

- 高码率／4K 的主动蓄缓存到达时限且仍未达到有效缓存目标后，同一 AVPlayerItem 不再重复主动暂停等待，仍保留 AVPlayer 自身的自动等待与持续停顿看门狗。
- 若当前为 Jellyfin 原画直放、服务器明确支持 Direct Stream，且后续仍处于等待并只有不足 2 秒的缓存，则只尝试一次原画兼容传输。沿用当前媒体版本、音轨／字幕选择、位置、倍速与用户播放意图；仍使用原生内核。
- 此次协商关闭视频转码，仅允许原视频复制。客户端还要求服务器返回 `VideoCodec=copy` 作为原画重封装／仅音频转换的证据。服务器未明确提供该能力时不自动尝试。
- 若此次兼容流无法协商、起播失败或首帧失败，则返回原画直放，保留暂停与位置；不会因为该尝试失败立刻请求 1080p／720p 转码，也不会循环重试。兼容流已经成功显示首帧后的实际长期故障继续遵循现有播放恢复策略。
- 播放设置增加“尝试原画兼容”，可手动发起同样的一次传输尝试；服务器明确不支持时隐藏该入口。画中画激活时暂不提供切换。
- 对来自 Jellyfin 的离线副本，播放设置增加“在线播放”，保留已下载文件，切回网络来源，继续保留当前位置及暂停意图。该覆盖只用于当前播放，不更改全局离线优先行为。
- 不引入网络 VLC 播放、WebDAV 增强或新的缓存文件；诊断 schema 保持 8，追加结构化事件码。

Jellyfin 定义中，Remux 保留音视频流，Direct Stream 保留视频并可转换音频：[官方说明](https://jellyfin.org/docs/general/post-install/transcoding/)。原画分段传输仍需要足够的持续吞吐；这次调整不能把不足的链路带宽变成足够带宽。

## 验证范围与证据

沿用原创 2160×3840、H.264 Main／5.2、SDR、50 fps、约 29.7 Mbps、60 秒样例。测试服务器只绑定 127.0.0.1，不读取用户媒体或服务器凭据。

直放 HTTP Range 在 8 MiB 处暂停供流 24 秒，模拟首帧后缓存长期积累不足；替代路径用 `ffmpeg -c copy` 将同一文件重封装为 fMP4 HLS。请求端断言关闭视频转码、允许复制、保持原画带宽上限。

原 MP4 与 HLS 的视频码流 SHA-256 一致：`fd6b38c1e31057dc7fb147b26b8e3cf9b9d21e85fc59f19192f1234827bc2558`。[哈希证据](Glide-1.3.0-transport-video-hash.json)。这证明本轮测试素材的视频流未重新编码；生产服务器的实际协商仍需通过播放诊断核对。

首轮 `/tmp/Glide4K/Transport-Build5-R1.xcresult` 通过，生产控制器 11 项检查通过：

- 主动等待 15.168 秒后仅约 0.052 秒缓存，随后自动改走原画重封装。
- 输出仍为原生 AVC 2160×3840，恢复前位置约 1.975 秒得到保留并继续推进；该段诊断上报 0 丢帧，但它只是模拟器短样例验证。
- 暂停时手动切换传输，位置与暂停意图保留。
- 实际下载原创样例后转为在线播放，已下载文件仍保留，暂停及位置保留。
- 模拟服务器拒绝兼容流，返回原画直放且保持暂停，未进入视频降档，也未重复协商。
- 服务器共收到 3 次原视频复制协商，所有请求均禁止视频编码。

[首轮结构化结果](Glide-1.3.0-transport-R1-results.json)。第二轮 `/tmp/Glide4K/Transport-Build5-R2.xcresult` 通过，13 项检查通过（121.406 秒）；增加服务器明确不支持分段时的重复停顿场景：原生报告 2 次停顿，但主动蓄缓存仅 1 次，第二次仍由原生自动等待，路由保持直放且 `recoveryCount = 0`。[第二轮报告](Glide-1.3.0-transport-R2-results.json)。

代码复核补充了“下载在在线播放期间完成”的竞态：手动原画传输尝试明确保留网络意图，避免重新解析时被刚完成的下载截获。最终扩展测试将下载步骤移到手动切换之前，`/tmp/Glide4K/Transport-Build5-R3.xcresult` 通过（112.272 秒），全部 13 项检查通过。[最终报告](Glide-1.3.0-transport-results.json)、[完成画面](Glide-1.3.0-transport.png)。

Core 回归已通过 96 项：92 项 Swift Testing、4 项 XCTest。首次新增状态测试因 Swift Testing 宏不能直接调用可变结构方法而编译失败，改为先执行状态迁移、再断言结果后通过；生产构建未受该测试语法影响。

普通流缓冲恢复回归 `/tmp/Glide4K/Native-Build5-Recovered.xcresult` 通过（156.268 秒），延迟恢复后仍保留原画流，只协商一次。[普通流诊断](Glide-1.3.0-transport-native-regression.json)。视频信息、原路径、30 秒缓冲目标、schema 8 以及手动原画传输入口的 UI 回归 `/tmp/Glide4K/Native-Build5-Info.xcresult` 通过（100.870 秒）。本轮 3 个不同的播放／界面用例均通过；原画专项的多轮不重复计数。

最终 Release 归档 `/tmp/Glide4K/Glide-1.3.0-5-final.xcarchive` 通过，确认原画传输恢复在发布可执行文件中，DEBUG 测试入口未进入发布包，原中文后备字体仍匹配源码。[归档审计](Glide-1.3.0-transport-release-audit.json)。最终设备包已成功重装到独立「Glide 兼容验证」1.3.0（5）；自动启动被手机锁定阻止。

用户随后反馈：Jellyfin 在线打开约 5–6 秒仍卡顿，手动切到“尝试原画兼容”后不卡顿。这是原片人工对照结果，支持改进默认传输选择；未附新的诊断，不能进一步锁定 Wi-Fi、NAS 或 HTTP 范围读取的具体根因。构建（6）据此推进开播前选择原画分段传输，后续验证单独记录。
