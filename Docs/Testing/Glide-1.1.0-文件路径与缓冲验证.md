# Glide 1.1.0（3）文件路径与缓冲增量

日期：2026-10-09。构建 2 已由用户确认测试完成并提交 GitHub；本文只记录本轮增量，不能沿用此前实机确认作为构建 3 的验收。

## 行为

- 播放设置 → 视频信息 → 文件，显示当前 PlaybackInfo 选中版本的原始路径；详情元数据作为后备，不误用其他版本的文件路径。信息页默认展开，路径完整换行、长按选择，复制后显示「已复制」。
- WebDAV 显示去除用户、密码、查询与片段参数的文件位置；本地／离线显示本机路径。Jellyfin 未返回路径时显示「服务器未提供」，不把认证流接口当作原文件路径。不增加起播前的元数据请求。
- 远程起播目标仍为 2 秒；首帧后按 30 秒实际观看时间增加目标，正常速度 30 秒、2× 60 秒。正常播放的明显缓冲等待至少 1.5 秒，恢复后提高至 45 秒／2× 90 秒，所有倍速目标最高 90 秒。新媒体重置，当前视频内部恢复保留；暂停、拖动和起播等待不触发增加。本地文件交由系统选择缓冲，不增加网络预取。
- 缓存条依旧取实际加载区间。视频信息里的「已缓冲」只计算当前位置所在连续区间的剩余时长，不把中间有空缺的已下载区间算入。
- 诊断 schema 5 新增 `forwardBufferTargetSeconds` 和 `bufferedAheadSeconds`，增加目标时记录 `buffer_target_increased`；路径不进入诊断导出。

## 实机复测

1. 电影、剧集与家庭视频各打开一段，进入视频信息。检查路径对应当前文件，中文和长路径可完整查看、复制；多版本分别切换检查，不能显示上一版本。
2. WebDAV 检查文件位置，离线影片检查本机位置。服务器不返回路径时确认明确提示；诊断导出不包含路径、服务器密码或令牌。
3. 在以前会卡顿的视频上，分别播放 1×／2× 至少 3 分钟，记录首帧、缓冲次数与秒数。起播前目标应为 2 秒，首帧后分别为 30／60 秒；遇到明显卡顿恢复后应为 45／90 秒。
4. 暂停、拖动、上下切视频再恢复，检查普通手势有效，缓冲目标不因拖动假增；新视频应回到正常目标。在实际缓存区间内外各拖一次，观察定位反应。
5. 弱网与高码率原画分别检查实际 `bufferedAheadSeconds`。若长期接近 0 且卡顿，提供 schema 5 诊断和网络／媒体信息，继续定位带宽、解码或服务器转码速度；不以目标数值宣称缓存已达标。

## 原生缓冲的限制

`preferredForwardBufferDuration` 是系统偏好，系统可因资源限制实际缓存更少；更高值也增加资源需求。短暂网络波动有机会通过已有缓冲吸收，持续供给不足不能靠提高目标消除。本轮不强制等待缓存满额才起播，也未量化证明真实 NAS 的卡顿率已经下降。依据：[Apple 原生缓冲说明](https://developer.apple.com/documentation/avfoundation/avplayeritem/preferredforwardbufferduration)。
